## 2024-03-20 - [Prisma Multiple Counts Optimization]
**Learning:** For Prisma database queries, executing multiple separate `count()` calls on the same table with different conditions causes unnecessary database roundtrips. Prisma's `groupBy` feature can calculate metrics for all statuses in a single query, significantly reducing latency and connection pool overhead.
**Action:** When a dashboard or aggregate view requires counts grouped by categorical fields (like `status`), always use a single `groupBy` combined with application-level reduction rather than issuing separate `count()` queries per status.

## 2025-02-17 - [Optimizing Wildcard String Matching]
**Learning:** The `matchPattern` function inside `packages/shared/src/index.ts` was compiling new regular expressions on every invocation by translating `*` to `.*`. When this matching is called inside loops (e.g., capability gate checks during tool invocation), the repetitive compilation produces a measurable CPU overhead. Replacing this with string operations (`startsWith`, `endsWith`, `includes`) for common patterns (e.g. `*`, `prefix*`, `*suffix`, `*substring*`) provides a massive speedup (~10x for simple string ops compared to regex). Using a Map to cache regex instances handles more complex patterns effectively without blowing up CPU. Furthermore, limiting the cache size prevents unbounded memory growth.
**Action:** When performing repeated wildcard or pattern matching, always attempt fast-path string operations first. Reserve Regular Expression compilation for truly dynamic/complex scenarios and employ a bounded cache (`Map` with `.size` checks) for the regex objects.
